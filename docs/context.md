## Data to use

### WaferLens simulated wafer maps (with ground truth)
Generated by `cd ~/waferLens && make simulate` (already present). Parquet, profile `demo`:
- `~/waferLens/data/demo/wafer_maps.parquet` (4.6 MB): `wafer_id int32`,
  `tested_at timestamp[us, UTC]`, `bin_map list<list<int16>>`.
  **Encoding: 0 = off wafer, 1 = pass, ≥ 2 = a fail bin** (bins 2–4 occur). FabEye's format
  (0 off, 1 good, 2 fail) is this with every fail bin mapped to 2.
  Sizes by product: **40×40 (9,774 maps), 30×30 (7,903), 24×24 (6,413)**; 24,090 sorted wafers.
- `~/waferLens/data/demo/wafer_pattern_truth.parquet`: `wafer_id`, `excursion_id`: which
  wafers carry an injected spatial pattern (wafers not listed have none).
- `~/waferLens/data/demo/excursions_ground_truth.parquet`: `excursion_id`, `excursion_type`,
  `chamber_id`, `spatial_pattern` (center, donut, edge_loc, edge_ring, loc, random, scratch),
  `start_time`, `end_time`, `magnitude_sigma`, …
- Wafers per pattern (demo): edge_loc 634, donut 367, random 315, center 215, edge_ring 164,
  loc 133, scratch 63. 13 spatial excursions in total.
- `dev` profile (1,000 wafers) in `~/waferLens/data/dev/` for fast tests; `stress` profile
  (125,000 wafers) in `~/waferLens/data/stress/` for throughput runs.
- Same data in Postgres (`cd ~/waferLens && make up`): tables `wafer_maps` (`bin_map
  smallint[][]`), `wafer_pattern_truth`, `excursions_ground_truth`, `wafer_patterns` (FabEye's
  predictions per wafer), `sort_bins`.

### WM-811K (real fab maps, labelled)
- `~/FabEye/data/wm811k/LSWMD.pkl` (raw, 811,457 maps), `processed_lot.pkl` (labelled maps,
  lot-disjoint split), loaded by `~/FabEye/data/wm811k.py` (`load_processed()`); 9 classes
  (none, Center, Donut, Edge-Loc, Edge-Ring, Loc, Near-full, Random, Scratch); 0/1/2 encoding;
  sizes vary (≈ 25×27 … 200+). Export to a compact binary format with a small script for C++.

### Baselines to compare against
- **FabEye CNN** (lot-disjoint test set): macro-F1 **0.858**; on WaferLens simulated maps:
  macro-F1 **0.909**, Random-class coverage 52% (strong random fields get called Near-full).
  Predictions per WaferLens wafer are in the `wafer_patterns` table (or run `make fabeye-report`
  in WaferLens). Service: `docker compose` service `fabeye` on :8000 (`/predict/batch`).
- **WaferLens batch pattern alarm**: caught 13/13 spatial excursions, median **52 h** after the
  excursion began, almost all of it sort lag (docs/root_cause.md in WaferLens). WaferEdge's
  closed loop measures the in-line part of that time.

## Open decisions (ask the user at the start)
1. **C++ standard**: install GCC 13 (`sudo add-apt-repository ppa:ubuntu-toolchain-r/test &&
   sudo apt install g++-13`, user runs it) for C++23 (`std::expected`, `std::print`,
   `std::mdspan` partly), or stay on C++20 with small polyfills. CUDA 12.4 accepts GCC ≤ 13.
2. **CUDA learning mode**: the user writes the kernels with guidance (concept → steps →
   reference values from the scalar backend to check against), or Claude writes them and the
   user studies them. Suggested: the user writes kernels 1–3 with guidance; Claude does the
   scaffolding, tests and benchmarks.
3. **Repo**: create `anson10/WaferEdge` on GitHub (public, MIT) at the end of phase 0, after

## Design sketch (to be refined in ADRs)
- `waferedge::core`: `WaferMap` (bin grid + metadata), views, loaders.
- `waferedge::signature`: features, clustering, Hough, randomness test, rule classifier.
  Backends behind one interface/concept: `scalar` (reference), `avx2`, `cuda`.
- `waferedge::secs`: SECS-II items (zero-copy decode, encode), message ids (stream/function).
- `waferedge::hsms`: framing, connection state machine, Asio coroutine sessions, timers.
- `waferedge::gem`: the GEM subset (comm/control states, S1F13, S6F11, S5F1, S2F41).
- `waferedge::pipeline`: SPSC rings, arena buffers, threads, decision rule, latency histogram.
- `tools/`: `tool-emulator` (equipment), `edge-host` (host), data export scripts.
- `python/`: pybind11 bindings.

**Why each piece is C++ (for interviews):** the decoder must not copy or allocate per message;
the pipeline's tail latency depends on lock-free hand-offs and no allocation; signatures run
per die over hundreds of thousands of maps; the GPU path needs explicit memory and stream
control. None of these are there "for show"; each has a measured requirement.

**Expected honest findings to look for:** GPU loses on single small maps and wins on large
batches (find the crossover); batching trades latency for throughput; classical rules are
explainable and strong on some patterns (center, edge-ring) and weak on others (random vs
near-full, loc); the in-line hold cuts the wafers exposed after detection to a few, while the
batch view is bounded by sort lag.

## Standards note
SEMI E5 (SECS-II), E37 (HSMS) and E30 (GEM) are paid standards. Work from public summaries,
open-source implementations' documentation and message layouts that are widely documented;
don't copy standard text into the repo. Say in the README that the implementation covers a
subset and isn't certified.
